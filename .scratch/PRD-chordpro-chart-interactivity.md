# PRD: Review chart interactivity (backlog #15 Phase 2, task #22 remainder)

Branch: `backlog/chordpro-review-chart-interactivity` (off `main` @ 71d5e07, after the
consolidation merge). Follows the confirmed decisions from Phase 2:
- Chord drag = free timestamp, no snapping (writes `EditableChordEvent.manualTime`).
- Confidence tint + Accept carry directly into the Review chart (no separate panel).
- Word/line correction writes `TimedLyricSegment.overrideText`.
- The spec-exact `ChordPro` tab (`ChordProReadOnlyView`) is untouched — this all lives in
  the Review tab's interactive `ChordProAppPreview`.

## Why this wasn't "free" once the schema landed

`ChordProAppPreview` doesn't render `AppModel.lyricSegments`/`chordEvents` directly — it
parses `model.chordProSource` (a plain ChordPro **text** string generated by
`ChordProDraftBuilder`) into a `ChordProPreviewDocument`. That builder reads raw
`event.time`/`segment.text`, never `effectiveTime`/`effectiveText`, so a drag or an edit
would be invisible until the whole chart regenerates (which only happens on
`applyAnalysis`, self-guarded once the chart is marked reviewed).

Rather than rebuilding the whole chart on every click (expensive, and would reshuffle
structure/spacing the user didn't touch), interactivity happens as an **overlay**: each
rendered chord/lyric line is matched back to its real `EditableChordEvent`/
`TimedLyricSegment` and the overlay reads/writes those objects directly. `AppModel`
already `didSet`-persists both arrays, so no new save path is needed.

## Matching a rendered chord back to its real event

`SongTimeline.Row.chordTimes` (already used for precise positioning, "B3") is the RAW
`event.time` for every chord on that row, in chart order, aligned 1:1 with
`ChordProPreviewLine.chords` whenever the previewed source is the current generated
draft. `EditableChordEvent.matching(rowTime:in:)` (new, pure, tested) finds the real event
by nearest raw `.time` within a small tolerance. Once matched:
- Its rendered TIME becomes `effectiveTime` (raw, unless a manual drag overrode it) —
  substituted into the times array `ChordProPreviewLineView`'s existing coordinate math
  already consumes, so no other change to that math is needed for the position to move.
- Its `confidence`/`accepted` drive the tint.
- Its `id` is the drag/tap gesture's target for `AppModel.setChordManualTime`/
  `toggleChordAccepted`.

Rows without a timeline (edited/legacy `chordProSource`) get `nil` matches throughout —
tint/accept/drag are simply unavailable there, same graceful-degradation convention the
codebase already uses for `rowChordTimes`.

## Matching a rendered lyric line back to its real segment

`SongTimeline.Row.kind == .lyric(ordinal:)` / `ChordProPreviewIndexedBlock.lyricOrdinal`
already indexes into `ChordProTabEditor.sortedLyricSegments` (same sort
`ChordProDraftBuilder` uses) — this is the exact mechanism `bassLabel(forLyricOrdinal:)`
already relies on. No new matching logic needed; just thread the segment itself through
instead of only its derived `words`/window.

## Word/line editing scope

The schema's `overrideText` is per-SEGMENT (whole line), not per-word — so "word editing"
in practice means a single-line correction, matching `LyricBlendRow.overrideText`'s
existing precedent. When a segment has a non-empty `overrideText`, the chart renders that
corrected line as plain static text (skips the rhythmic per-word placement and the
bouncing ball for that line specifically) rather than trying to re-derive fake per-word
timings for hand-typed text. This is a deliberate, bounded trade-off: correcting a line
gives up its word-level highlight granularity, gains a corrected display.

## UI placement

- Chord tint + tap-to-accept + drag-to-reposition: on the chord `Text` itself, inside
  `ChordProPreviewLineView` (both monospace and rhythmic render paths) — inherently
  coordinate-dependent, so it stays in the one view that already owns that math.
- Lyric line accept toggle + edit-pencil trigger: a small sibling control row in
  `ChordProPreviewBlockView` (NOT inside the coordinate-heavy line view), toggling a local
  `@State` between the normal line render and a plain `TextField` seeded with
  `effectiveText`.

## Out of scope / explicitly deferred

- Snapping/quantizing chord drags to the beat grid (Eric confirmed: free timestamp).
- Per-word editing UI (schema doesn't support it; would need a new field).
- Any change to the spec-exact `ChordPro` tab.
